Windows Sonic and DTS Headphone:X are separate loading investigations. No custom listener import or converter is established yet, and no live audio configuration was changed. The requested next outcome is a native loading proof before any SOFA converter.

Microsoft's public spatial-object activation structures expose source format, object counts, directivity, distance, environment and orientation parameters, without a listener coefficient buffer or SOFA path in those inspected structures. This is a boundary of the documented interfaces, not proof that private loading is impossible. Sources: Spatial Sound (historical reference unavailable)

For Sonic-related components, the inspected HrtfApo.dll is version 10.0.26100.4202, SHA256 ffc12d088cc02441061cc2bb7f3b367fe8089662e0fd61ab98209ef6d43b6489. Its initializer 0x180009ec4 obtains mapped data through SpatialSoundDataManagerRpc, loads HrtfDspCpu.dll, resolves CreateHrtfDataHelper, and passes mapped data into that helper. The analyzed count is bounded at eight. REA evidence ev_098d9c17b501f4ab9d856b0662908ce5f0e17fc5dc9e497bea0d4aca2253153e preserves the complete pseudocode and limitations in windows_sonic/HrtfApo_REA_evidence.json. RPC binding and operation-zero client dispatch are separately retained there.

The registry Hrtf path points to DefaultHrtfs.bin. HrtfApo's registry-reference function checks availability; it does not itself prove that changing the path changes loaded data. Ghidra analysis of audiosrv.dll identifies registration of the RPC endpoint at 0x1800cce10 and a delayed import of s_RequestHrtfData from SSDM.dll. The saved audiosrv_pivots.txt and audiosrv_imports.txt establish that server boundary. SSDM.dll and HrtfDspCpu.dll parsing, integrity checks, cache lifetime, dataset selection, and linkage to the selected Windows Sonic system renderer remain to be traced. XAudio2 HRTF APIs must not be mistaken for a system-wide Sonic profile-import API.

The inert DtsHrtfEnc.dll is SHA256 90e62a7f6d044b43e53413f1f0933647725838f60904de37cd4b49f3852a604c. Function 0x180004788 retrieves RuntimeSettingsBLOB and DeviceProfileSettingsBLOB from a property bag and retains their byte arrays. Its caller 0x180003a40 routes them through 0x180004f94, 0x180007a40, 0x180005c8c and 0x1800060f0 into native processing initialization. Runtime data is validated by 0x18000bec8 as SPAC version 2; 0x18000b394 sizes response data and 0x18000b494 copies or resamples it. Complete REA records are in dts/DtsHrtfEnc_REA_evidence.json, including ev_24312aa2ae8b4de1f3865bb286578881a58fa8dfb5df8990481dbd4bcf1926fe and ev_83e37498321423bb691d579f41fc1dbe60e482c5505fe28f8e0d42712c5e14a6.

An embedded default runtime blob begins at native address 0x180030d20, mapped file offset 196896, with 230300 bytes. It contains an RCHN block with 48000 Hz, count 14, mask 3; both response tables have 1024 samples and 28 floating-point response arrays. An RPAN block follows. The read-only inspector tools/inspect_dts_spac.py verifies byte extents, tags, versions, dimensions and finite response values on this observed carrier; three tests pass on the installed Python 3.8 runtime. It does not validate the native format completely or label ear ordering or direction ordering.

DTS's remaining concrete questions are which persistent app/endpoint setting produces each property-bag blob, the table and RPAN direction ordering, ear ordering, full validation rules, cache/update notification behavior, and the processing consumers for dynamic objects. The observed carrier is a loading candidate, not a demonstrated custom import. Do not write either blob or mutate any dataset path before a reviewed live test and exact restoration plan.
