Static native analysis now establishes the canonical explicit-HRIR serialization used by the Sonic CPU dataset helper. No custom Sonic dataset was installed, and no Sonic DLL was executed.

Pinned `HrtfDspCpu.dll` SHA-256 `4706985ccbc44d74a9060df72c6ae7c7f34e95aeee5d99669fd00ea8d74261f9`, Ghidra 12.1.4. Full observations are retained in REA evidence. These are serializer/parser contracts, not a completed SOFA converter or active-state proof.

The main block begins with GUID `<identifier-removed>`, then little-endian uint32 sample rate and position/filter count at offsets 16 and 20. Constructor `HrirData_impl` 0x18000daac requires positive values, computes the position-block extent from count, copies that block to its owned storage, and decodes two `ImpulseResponseSet` blocks. The two sets reside at object+0x30 and +0x48. Full physical-ear assignment is not established by that constructor alone.

Coordinate serialization 0x18001104c writes GUID `<identifier-removed>`. Its canonical header is 32 bytes: uint32 data offset 32 at +16, count at +20, and stride at +24. The stride is `align_up(4*count,16)`, established by 0x180009ad8; header size comes from 0x180010cc0. Total coordinate extent is `32+3*stride`. X, Y and Z are separate float32 arrays at offsets `32`, `32+stride`, `32+2*stride`; padding does not add positions. The AoS constructor 0x18000d8b4 separates its three input components into those arrays before serialization. No triangulation table is serialized by this routine. Coordinate interpretation at the actual object consumer still needs a separate trace.

View decoder 0x1800111c8 checks the GUID, extent, stride and 16-byte alignment of its input pointer, then returns pointers into the separate arrays. The main HRIR constructor copies coordinates into aligned owned storage before invoking this view; file offset 24 is not itself a requirement for an aligned caller buffer. Canonical writer header+28 and alignment padding are not assigned semantic fields by this evidence.

Each response set begins with GUID `<identifier-removed>`, uint32 header size 24 and response count. It contains `count` uint32 lengths followed by sequential float32 responses of those lengths. Extent is `24+4*count+4*sum(lengths)`, established by 0x1800103bc and writer 0x1800103ec. The pointer/length constructor 0x1800100d4 rejects zero response lengths and concatenates the supplied arrays. The main serializer 0x18000dd00 writes the sample rate/count, position block and both response sets; size function 0x18000de40 combines their extents.

HrirData's actual vtable at 0x180141738 has conversion method 0x18000dea0 at slot +0x20, the method invoked by `HrtfDataHelper` 0x1800057e0. It decodes the coordinate view and constructs `HrtfData_impl` via 0x18000d5d8. That constructor converts both response sets independently through 0x18000f2f8, and copies the coordinate arrays. TransferFunctionSet construction divides each response into `ceil(length/block_size)` partitions, zero-pads the final partition and applies transforms of length `2*block_size`. The selected path therefore consumes explicit impulse-response samples into partitioned transfer data; it does not show an HRTF basis fit or automatic onset/tail trimming. Native transform normalization and physical-ear output routing still require downstream verification.
