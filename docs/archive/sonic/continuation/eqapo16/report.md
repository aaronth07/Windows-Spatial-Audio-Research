# Object rendering to sixteen-channel Equalizer APO convolution

Actual Windows spatial object input now passes the numerical chain: PCM and position captured before Windows mixes it → VBAP speaker panning → sixteen float channels → the installed Equalizer APO DSP → full SOFA convolution. The input capture runs live; the verified custom rendering of that capture runs offline. A live custom-output pump and arbitrary game interception remain unperformed. No endpoint/default/provider configuration or installed Equalizer APO file was changed by this work. The master configuration hash is checked before and after each APO suite; the latest pair matches.

## Verified processing

`vbap_probe.cpp` implements vector-base amplitude panning for explicit spherical speaker coordinates. Six independent-reference cases cover 4, 8, 16, 24 and 32 output channels, including 64 moving objects into sixteen channels. The listener must lie within the supplied geometry's directional coverage. Positions use SOFA axes: front, left, up. The Windows right/up/back coordinates require an explicit conversion. Source gain is applied once, independently of the normalized panning gains. The 128-sample transitions interpolate panning weights; the target-direction error metric does not establish a constant-angular-speed trajectory during the transition. Original VBAP paper`. The native v2 carrier preserves lifetime IDs, resets pan/gain state when an ID changes, and keeps prior convolution tails. Panner error is at most `4.55e-13`; complete APO-chain error is `6.33e-12`, or `3.83e-7` relative to peak. All 4,096 taps and the final tails are included; the other fourteen output columns are zero.

The converter explicitly aligns these two recordings at producer sample zero. That is an offline comparison convention, not measured device alignment. The actual streams are the interleaved owned producer described in `../live_object_tap_multistream/report.md`; this does not establish arbitrary COM threading or existing-game compatibility. `../system_object_input/root_chain_review.md` records the independent code review, a corrected malformed negative-offset bug, a decisive pan/gain lifetime-replacement case and a separate complete numerical reproduction. `capture_negative_review/result.json` rejects nine corrupt captures before native rendering. Exact integer record extents, contiguous updates, ID ownership, EOS/replacement generations, finite volume and PCM identity are checked.

A WinDbg-engine breakpoint in `debug_verified.log` identifies the real `IAudioProcessingObjectRT::APOProcess` implementation at the pinned DLL's RVA `0x70000`, with one input/output connection and a valid 128-frame property record. The nearest-export debugger label is not a private function name. Earlier `debug.log` did not execute the intended breakpoint script and is retained only as an unsuccessful debugging attempt.

## Route limits and remedies

Ordinary Equalizer APO convolution requires a fixed processing quantum in these tests. Alternating callback sizes yields incorrect samples with intact external buffer guards. The source corroborates a convolver prepared for one partition length, including a first-call smaller-size reinitialization path. `FixedQuantum` successfully coalesces variable producer packets into constant 128-frame processing. It is not a complete live callback transport: its caller must add an output FIFO, pad a final partial quantum and submit the FIR tail as valid zeros.

The isolated host's missing endpoint-install information leaves `allowSilentBufferModification=false`. Under that policy, `BUFFER_SILENT` suppresses a filter tail. Valid zero PCM retains it. Equalizer APO has a separate policy branch that preserves nonzero tails; the counterexample is not a universal limitation of every installation. `processing_diagnosis.md` records this distinction and the source/trace evidence.

The stock APO's public format negotiation rejects a sixteen-input/two-output graph: the actual DLL returns `S_FALSE` and suggests two input channels (`query_downmix.json`). The verified matrix therefore keeps sixteen physical output columns, with only columns 1/2 used. An application hosting the DSP can explicitly route those two columns to a stereo sink; a live sixteen-channel endpoint needs an explicit downstream route. Adding a Copy matrix does not change the endpoint's negotiated channel count.

The current read-only endpoint query finds an existing sixteen-channel virtual endpoint at 48 kHz, minimum reported shared period 48 frames and default 480. It advertises zero dynamic spatial objects in that configuration. selected virtual endpoint advertises 128 dynamic objects and a two-channel mix. These observations establish separate endpoint capabilities, not an object-to-sixteen-channel connection. `audio_capabilities_current.log` records the query; no streams were started by that utility.

Getting the original objects from an already binauralized stereo loopback is ruled out as a general, unique reconstruction method. `stereo_nonuniqueness.py` constructs three nonzero causal source signals using three actual SOFA filter pairs whose stereo sum cancels to numerical roundoff (`1.39e-17`). Distinct object inputs can produce the same stereo output even with perfectly known filters. This does not restrict access before mixing.

## Latency and remaining integration

At 48 kHz, a 128-frame block spans 2.667 ms; packet accumulation can add up to 127 frames before processing. The APO reports zero additional latency in this host, and direct-reference comparisons need no extra whole-block offset. The FIR's own timing remains in its coefficients. CPU execution, accumulation, source packet duration, device queue and clock drift must remain separate quantities. The native panner's 64-object→sixteen-channel test cost at most 0.3502 ms per block in the second review; the sixteen-channel SOFA APO matrix at most 0.3444 ms in that run. Those were separate offline measurements under ordinary Windows scheduling, not a combined deadline or end-to-end measurement.

The implementation can be used for application-owned objects. Actual process-local interception is verified through a separate producer DLL's normal COM/Windows spatial calls, not a mock spatial service. The original native stream still renders; the current capture proof does not suppress that native output or send the custom result to a device. A synchronous observer immediately before forwarding EndUpdatingAudioObjects is the concrete integration point. A live implementation still needs a bounded output FIFO, clock policy, real-device callbacks and explicit handling of native-output duplication. Multiple independent sources or physical devices may need asynchronous sample-rate conversion; short clock fits do not establish long-term drift.

`../live_object_clock/report.md` found different inferred stream clock origins in one trial. `../live_object_latency/report.md` subsequently identified two independent live source signals in same-endpoint WASAPI loopback: their output peaks coincided within one capture sample in that different trial. The API-timestamp-based peak was 26.367–26.456 ms after the first submission call midpoint. This includes the current selected provider, postmix and endpoint path. The virtual endpoint's API packet timestamps were ahead of host retrieval, so this is not an acoustic or independently calibrated hardware latency measurement, nor a Sonic-only or custom-APO-chain result.

A system-wide route still needs an admitted provider/effect insertion or compatible application interception. A game need not expose its original objects to an ordinary post-mix APO. Sixteen virtual speakers approximate arbitrary source directions; they do not preserve every direction as exactly as direct per-object SOFA rendering. WSSAPI accepts object PCM from the application; this proof is object rendering/channel conversion, not compressed Atmos or DTS codec decoding.
