# Endpoint effect bootstrap: proposed decisive test

Status: inert APO and owned COM-host tests passed; actual system admission/selection remains unperformed. This document performs no registration, endpoint change, process attach, playback or recording. The parent coordinates the exact system test and backup/restore procedure within the existing user scope; process-wide effects and changes beyond selected virtual endpoint remain unresolved.

The candidate is an admitted endpoint effect whose constructor or Initialize explicitly loads an owned CPU-factory DLL before Sonic's first HrtfApo engine creation. The isolated preload already works with the zero GUID and both CPU exports. Static construction code establishes a plausible per-pipe interval before locking. It does not establish the actual target endpoint's node list or first-load order across pipes.

The read-only host probe found one audiodg process, but Win32_Process returned null ExecutablePath and CommandLine. Sixty-four existing events from each of the enabled Audio Operational and PlaybackManager logs exposed endpoint-state notifications or producer/session events, without a payload linking the chosen endpoint to that audiodg PID. The event system's emitting PID must not be treated as the endpoint host. These bounded observations do not prove that no other mapping interface exists. Current evidence does not satisfy host isolation; a safe live renderer-selection experiment must wait for an explicit endpoint-to-host mapping or a tested per-engine endpoint identity. The inert admission/timing stage can be planned separately.

The inert APO has been built as bootstrap_apo.dll. Its owned COM host passes 48 exact PCM/silence/in-place/frame cases and eight oversized-frame rejections. Startup logs contain at most 64 fixed BootstrapEvent records. Phase1=constructor,2=Initialize before optional preload,3=lock,4=unlock,5=destructor,6=Initialize after optional preload. No logging or loading occurs in APOProcess or a custom DllMain. The default unconfigured object does neither. The test records a supplied synthetic PKEY_AudioEndpoint_GUID; module path and disk SHA-256 are independently checked. It also exercises discovery without preload, rejection without supplied endpoint GUID, missing-export rejection and log-capacity/overwrite bounds.

Two tested configuration paths now exist. ConfigureBootstrap(fullNewLogPath, enablePreload, fullCpuPath) is an owned-host helper called before construction. The system candidate instead reads private properties from the supplied APO system-effects property store during Initialize; it requires an absolute new log path and, for preloading, an absolute factory path plus approved SHA-256 and supplied endpoint GUID. Thirteen owned-memory property cases passed without the Configure export. No live registry values were written. Details are in bootstrap_properties.md. Property-based setup cannot log construction before Initialize receives the settings. Existing-module hashes identify disk files, not mapped-memory byte integrity.

The future reversible system test should establish these facts separately:

1. Admission: the approved endpoint actually constructs/initializes the inert APO, with the expected module hash. Failure is an admission/configuration observation, not proof that custom DSP is impossible.
2. Timing: initialization reports that the native CPU module is absent. A subsequent selected spatial path creates an engine. Existing-module presence means this preload opportunity was missed; do not unload/replace the system module in place.
3. Selection: after an approved fresh host lifetime, enable the owned CPU module and require a positive custom-factory creation marker and custom Render marker with validated source record dimensions. Loading the module or CoCreateInstance success alone does not prove provider selection.
4. Scope: prove which endpoint/pipe the selected engine belongs to, or demonstrate exclusive host ownership. Basename resolution affects the whole process. Do not claim endpoint isolation from endpoint registration alone.
5. Restore: restore the exact approved endpoint effect configuration and registration, end the approved host lifetime through the agreed mechanism, then verify baseline hashes/configuration/provider selection. No restoration procedure is executed by this plan.

Use a pass-through mode before custom audio. The current diagnostic channel-routing mode is intended for owned hosts and must not accidentally be selected for a live endpoint. Full SOFA preparation must finish outside a real-time callback. A production design also needs concurrent-engine state, ref-counted module ownership and source lifecycle handling; the current prototype deliberately uses one configured engine at a time and keeps the data-helper module reference until process exit.

Current machine evidence from the parent's host_policy_observation.json reduces an assumed unsigned-module barrier but does not substitute for admission and timing observations. No driver install, global audio security change, vendor package spoofing, system DLL replacement or modification of a running audio process is part of this candidate.
